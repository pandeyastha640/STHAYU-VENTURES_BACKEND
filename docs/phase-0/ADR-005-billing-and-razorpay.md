# ADR-005 — Billing & Razorpay Integration

**Status:** Accepted (Phase 0)
**Date:** 18 August 2026
**Phase:** 0 — Product Clarification & Architecture

## Context

User locked decision: **Razorpay only** (India market). Subscription plans already on the marketing site:
- Starter ₹9,999 / month
- Growth ₹24,999 / month
- Scale ₹49,999 / month
- Enterprise (custom)

Phase 0 unit economics (see `unit-economics.md`) shows Starter plan has thin margin; Growth and Scale are healthier. Pricing may need adjustment before launch — flagged for decision in Phase 0 review.

Requirements:
- Customer subscribes → entitlement activates
- Customer upgrades/downgrades (prorated)
- Customer cancels
- Failed payments → dunning
- Invoices with GST (India)
- Webhooks verified

## Decision

### Razorpay products used
- **Razorpay Subscriptions** for recurring plans (Starter, Growth, Scale)
- **Razorpay Payment Links** for one-off Enterprise onboarding (Phase 1 simple version; full enterprise contract flow in Phase 2)
- **Razorpay Webhooks** with signature verification
- **Razorpay Invoices** generated by Razorpay (we mirror in our DB for fast queries)

### Plan model in our DB
- `plans` table holds: code, name, price_paise (integer to avoid float issues), currency (`INR`), interval (`monthly` | `yearly`), interval_count, razorpay_plan_id, features JSONB, limits JSONB, is_active, display_order.
- Seed data for Starter / Growth / Scale (monthly + yearly variants where applicable).

### Subscription model
- `subscriptions` table holds: organization_id, plan_id, razorpay_subscription_id, status (`created` | `active` | `paused` | `cancelled` | `completed` | `past_due`), current_period_start, current_period_end, customer_id (Razorpay customer), created_at, updated_at, cancelled_at.
- One active subscription per organization at a time.

### Lifecycle
```text
Customer clicks "Subscribe" on Growth plan
   ↓
Backend creates Razorpay Customer (idempotent by org_id)
   ↓
Backend creates Razorpay Subscription
   ↓
Backend returns subscription.short_url (hosted checkout) to frontend
   ↓
Customer completes payment on Razorpay
   ↓
Razorpay fires subscription.activated webhook
   ↓
Backend verifies webhook signature
   ↓
Backend updates subscriptions row to status=active
   ↓
Backend updates organization entitlements (cache + DB)
   ↓
Customer redirected back to /billing?status=active
```

### Webhook handling
- Endpoint: `POST /v1/billing/webhooks/razorpay`
- Header: `X-Razorpay-Signature` verified using `RAZORPAY_WEBHOOK_SECRET`
- Events handled: `subscription.activated`, `subscription.cancelled`, `subscription.completed`, `subscription.paused`, `subscription.resumed`, `payment.captured`, `payment.failed`
- Idempotency: webhook event IDs stored; duplicates ignored
- Retries: Razorpay retries on non-2xx for 24h; we always return 200 quickly and process async

### Upgrade / downgrade
- Upgrade: cancel old subscription, create new subscription with `start_at` = current period end (no charge gap) or prorated by Razorpay's "schedule changes" feature in Phase 2.
- Downgrade: schedule change at period end (no immediate feature loss).
- v1: simple "cancel old + create new" pattern. Refine in Phase 2 with Razorpay Subscription "change plan" API.

### Cancellation
- User clicks cancel → soft cancel (subscription stays active until period end, then status=cancelled).
- Option to "cancel immediately" with prorated refund handled manually in Phase 1 (full automation Phase 2).

### Dunning
- Razorpay handles retry logic for failed payments.
- We send email notifications (via Resend) on `payment.failed`.
- After 3 failed retries (Razorpay default), subscription auto-pauses.
- Customer's workspace enters "limited" mode (read-only) when past_due.
- After 7 days past_due, subscription cancels and workspace is deactivated.

### Entitlements
- Computed in a `getEntitlements(orgId)` function that reads the active subscription + plan.
- Cached in Redis with TTL 60s; invalidated on webhook.
- Enforced server-side on every relevant endpoint.

### GST (India)
- Razorpay handles GST collection by default if customer's GSTIN is provided.
- We collect GSTIN at signup (optional field).
- Invoices include Sthayu GSTIN, customer GSTIN (if provided), HSN/SAC code (998314 for SaaS).
- Invoice mirrored in `invoices` table for query speed.

### Refunds
- Manual in Phase 1 (admin issues via Razorpay dashboard).
- Self-service refund UI in Phase 2.
- Refund policy: pro-rated unused period minus 5% processing fee.

### Annual plans
- Razorpay Subscriptions supports yearly intervals. Add yearly variants in Phase 1 if margin allows (10-15% discount on annual vs monthly). Phase 0 unit economics flags this for review.

## Consequences

- One payment gateway to integrate (Razorpay).
- India-only for v1 (no Stripe, no international cards).
- All billing webhooks are signature-verified and idempotent.
- Customer never sees raw card forms (Razorpay-hosted checkout).
- Entitlements cached, not recomputed on every request.

## Open items (flagged for Phase 0 review)

- Pricing: Starter ₹9,999 may have thin margin. See `unit-economics.md`.
- Annual discount: 10% or 15%?
- Free trial: 14-day on Growth (per locked decision Q8). Razorpay trial configured via `start_at` delay or `offer` trial.

## Alternatives Considered

| Alternative | Verdict |
|---|---|
| Stripe | Rejected — user chose Razorpay only |
| Build our own billing logic | Rejected — Razorpay does the hard parts |
| Chargebee / Recurly | Deferred — Razorpay sufficient for India MVP |
